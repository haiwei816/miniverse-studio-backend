# ADR-0001：模块化单体与同步事务

状态：本地 MVP 已采用。

背景：两款独立游戏共用身份、存档和运营能力，流量尚不足以证明分布式服务的成本合理。奖励和审批的一致性优先于异步扩展。

决定：普通业务在单个 Go API 进程内运行，按身份、存档、活动、奖励、排行、GM、渠道和策划分文件；平台验证单独包，C++ 使用明确 Protobuf 边界。database/sql + MySQL 表保存权威数据。服务层共享单个显式事务边界，内部不引入消息中间件。当前 service 包边界较粗，后续模块变大时按数据所有权拆包，不先创建空接口。

事件→去重→活动进度→奖励流水→邮件创建在同一数据库事务完成。领取时锁邮件并原子增加库存。这样没有活动完成与邮件投递之间的崩溃窗口；补建奖励端点可对旧数据安全重试。业务键包含游戏、玩家、活动版本/日分桶或赛季/GM申请。MySQL 死锁和锁等待超时允许有限重试，其他错误不会被重试掩盖。

存档 revision 在锁内比较，删除也增加 revision；历史恢复产生新版本。GM 审批与执行、审计一并提交，申请人与审核人必须不同。回滚配置创建新版本并再次审核，不重写历史。

后果：部署与恢复简单，事务保证清晰；单榜单写入按榜单锁序列化，列表和排序适用于小型 MVP。遇到实测瓶颈时再考虑分页、批次任务和 outbox；拆服务时必须保留同等幂等和可恢复语义。

C++ 按需验证，与普通运营能力无启动依赖。确定性回放与对局真实性是不同保证，不能以一个验证通过的客户端回放承诺强反作弊。
