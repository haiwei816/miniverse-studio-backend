# 内存与架构复核 — 2026-11-06

## 结论

Go 模块化单体 + MySQL 可以继续支撑“多款自有游戏共用账号、存档、活动、邮件、排行和运营后台”的目标。当前代码是经过本地验证的 sandbox MVP，尚不能作为截图所示完整商业运营后台交付。架构可扩展与功能已实现需要分开判断。

内存方面发现并修复两项真实风险；本轮短时检查没有观察到持续的 Go 堆、goroutine、文件描述符、数据库占用连接或 Godot 节点泄漏。没有执行数小时/数天 soak test，也没有给第三方 gRPC 库作完整进程级泄漏认证。

## 已修复

1. 限流表原来只在条目超过 10000 时清理已过期来源，同一分钟内大量不同 IP 仍可无限增长，之后还会对每个请求全表扫描。现在设定硬上限 10000；满表时拒绝新来源，保留已有来源计数；有流量时每分钟回收过期条目，无额外常驻 goroutine。空闲时最多保留这 10000 个条目的有界内存。
2. 排行榜原来把整赛季装入 Go slice，再截取 Top50/附近名次，结算也加载全榜。现在用数据库窗口排名返回最多 50 或 5 条，结算只读取前三名。排序和精确名次仍有数据库计算成本，需要在真实规模下检查执行计划；本改动限制的是 Go 端驻留量。

## 实测证据

| 检查 | 结果 | 边界 |
|---|---|---|
| 限流并发与过期 | 20000/32000 个模拟来源后不超过 10000，过期可回收，竞态检查通过 | 不是分布式全局限流；满表时新来源会收到429 |
| Go + 真实 MySQL + gRPC | 2530 次档案读取，280 次 gRPC，5 批次后 GC 堆 1159120→1101488 bytes | 测试本身约7.8秒，不能替代长时运行 |
| goroutine / FD | 预热后到结束均为 4 / 8 | 单个集成测试进程，含实际 gRPC 客户端创建与关闭 |
| 数据库连接 | open=1、in_use=0，所有样本稳定 | 服务池上限16，检查覆盖本轮读取/回放路径 |
| C++ | ASan + LSan + UBSan，200000 合法与200000非法回放，退出0，无诊断 | 覆盖纯规则核心；系统 gRPC 依赖未整体重新 instrument |
| Godot | 100次客户端创建/请求/释放后，节点和孤儿节点回到基线 | 覆盖成功请求生命周期；不是整个游戏的内存认证 |
| 大榜单 | 20001条成绩，返回Top50/附近5，精确并列名次10001，结算仅3笔奖励 | 测试数据已清理 |
| 回归 | 原赛季三模式与gRPC成绩校验测试通过；Go race/vet通过 | 真实平台/AI依然未验证 |

Go 堆快照：memory-before.pprof、memory-after.pprof；采样：memory-results.json。命令和原始输出见 memory-integration.log、memory-cpp.log、memory-review-go.log。Go runtime 持有内存、MySQL buffer pool 和系统 allocator 的保留不自动构成泄漏，应结合 GC 后活对象与长期趋势判断。

## 架构调整方向

保留 Go 单体和 MySQL，优先补清楚数据所有权与业务契约。

- 身份层：内部账号 → 游戏档案；有区服/多角色的游戏增加区服 → 角色。先保留现有API兼容，再做明确迁移，不能把 game_id 当作 server_id。
- 共享运营层：管理员、游戏/区服授权、审批审计、公告、邮件、奖励账本、活动与任务调度。
- 每游戏扩展层：显式注册玩家概览、道具目录、专属数据查询和操作校验。GM依赖有权限检查的稳定接口，不直接任意修改云存档JSON或拼SQL操作游戏表。
- 查询层：玩家详情、日志、流水和活动配置列表增加游标分页、时间范围与查询上限。大数据量用汇总读模型，后台报表避免拖慢玩家请求。
- 执行层：大批次发奖、广播邮件、定时活动和赛季结算使用可恢复任务状态机及稳定业务键；现有同步事务可继续用于小批操作。

生产最先补齐的实际缺口：真实登录适配与会话发行、管理员安全初始化、区服/角色（如游戏需要）、封禁/举报工单、生产榜单/结算管理入口、生命周期数据清理、备份恢复与持续监控。目前游戏注册、榜单配置和结算入口只在 sandbox 开放，不能把切换 APP_ENV 当成生产落地。

会话、nonce、事件、回放、审计和存档历史目前会持续增长在数据库中。这属于数据保留/归档缺口，不是本轮证实的 Go 内存泄漏。清理会话/nonce前需索引和批次上限；清理业务幂等记录或奖励流水前必须保留足够的防重放/审计依据。

活动当前覆盖累计、每日、签到、里程碑的固定规则。复杂开放条件、跨任务链、连续签到、任意脚本、完整MMO社会系统不应被描述为已经具备。C++当前只提供一个确定性卡牌规则样例，真实渠道和AI均为明确的后续适配项。

在仓库根目录，先启动 `docker compose -f deploy/compose.yaml --profile rules up -d --build`。


运行范围仅限本地测试工程。测试随机创建自身数据并清理其成绩/奖励；不向参考网站发送任何业务操作。
